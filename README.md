# Performance Terminal

A private Streamlit application for tracking the real-world performance
of signals generated by the **Nifty Market Terminal**.

The app freezes daily Buy List, Confluence, and other supported signal
outputs into a single master database, tracks their subsequent market
performance, consolidates repeated signals into trade episodes, and
generates investor-friendly performance summaries.

## Core Design

The application uses **one master CSV as the database**:

``` text
performance_database.csv
```

Every signal occurrence is stored permanently.

For example, if the same stock appears repeatedly:

``` text
25 Aug 2026   Confluence   ABC
26 Aug 2026   Confluence   ABC
27 Aug 2026   Confluence   ABC
```

All three records remain in the database. This preserves the complete
historical record of what the scanner generated on each date.

The app then creates different analytical views from the same master
CSV.

# Features

## 1. Cohort Freezing

A daily signal list can be frozen into the master database.

The frozen record preserves the information available at the time of the
signal, including:

-   Cohort date
-   Signal type
-   Symbol
-   Company name
-   Entry price
-   Score or conviction
-   Setup information
-   Relevant metadata available in the imported list

Once saved, the entry information remains historically preserved.

## 2. Master CSV Database

The application uses a single persistent file:

``` text
performance_database.csv
```

The database grows over time as new cohorts are added. Historical
records are **not deleted after a performance horizon is reached**.

The database is designed to retain the complete historical record for
future analysis.

# Performance Methodology

The application uses **standard calendar-based investment horizons**
rather than arbitrary trading-day counts.

## Checkpoints

``` text
Entry
1D
1W
1M
3M
6M
1Y
Trailing Profit
```

### Entry

The entry price is the frozen closing price associated with the cohort.

### 1D

The next available trading session after the cohort entry.

### 1W

One calendar week after the entry date.

### 1M

One calendar month after the entry date.

### 3M

Three calendar months after the entry date.

### 6M

Six calendar months after the entry date.

### 1Y

One calendar year after the entry date.

This approach makes the results easier to compare with the return
conventions commonly displayed by investment platforms, benchmarks, and
professionally managed investment products.

## Non-Trading Days

For calendar-based checkpoints, the application calculates the target
calendar date.

If the exact date is not available in the market price history because
of:

-   Weekends
-   NSE holidays
-   Market closures

the application uses the **most recent available trading close on or
before the target date**.

Example:

``` text
Entry Date: 25 August
1M Target Date: 25 September
If 25 September is a Sunday:
Use the latest available market close before 25 September.
```

This creates a consistent calendar-period measurement framework.

# Trailing Profit

`Trailing Profit` is the live return from the frozen entry price to the
latest available market close.

Formula:

``` text
Trailing Profit (%) = ((Latest Available Close / Entry Price) - 1) × 100
```

Example:

``` text
Entry Price: ₹100
Latest Price: ₹118
Trailing Profit: +18%
```

Unlike the fixed checkpoints such as `1M` or `3M`, Trailing Profit
continues to update whenever performance data is refreshed.

It answers:

> If the stock had been held from the original signal until today, what
> would the current return be?

# Two Performance Views

## 1. Signal Performance

This is the raw historical view.

Every occurrence of a signal is treated as a separate observation.

Example:

  Cohort Date   Signal       Symbol     Entry   Trailing Profit
  ------------- ------------ -------- ------- -----------------
  25 Aug        Confluence   ABC         ₹100              +15%
  26 Aug        Confluence   ABC         ₹103            +11.7%
  27 Aug        Confluence   ABC         ₹105             +9.5%

This view is useful for answering:

> How did every individual signal generated by the scanner perform?

Repeated appearances are intentionally retained because they are
separate scanner observations.

## 2. Consolidated Trades

The Consolidated Trades view groups repeated consecutive appearances of
the same stock and signal into a single trade episode.

Example:

``` text
25 Aug   ABC appears in Confluence
26 Aug   ABC appears again
27 Aug   ABC appears again
```

The consolidated view can display:

  ------------------------------------------------------------------------------
  Symbol    Signal Type  First     Latest           Entry     Trailing Outcome
                         Signal    Signal                       Profit 
  --------- ------------ --------- --------- ------------ ------------ ---------
  ABC       Confluence   25 Aug    27 Aug            ₹100         +15% Winner

  ------------------------------------------------------------------------------

This prevents repeated signals from artificially inflating:

-   Trade count
-   Win rate
-   Winners
-   Losers
-   Portfolio exposure

The consolidated view is designed to answer:

> If an investor treated repeated appearances as one continuing idea,
> how did the trade perform?

# Trade Outcome Filter

The Consolidated Trades view supports outcome filtering:

``` text
All Trades
Winning Trades
Losing Trades
Neutral Trades
```

Trades are classified using their current Trailing Profit.

The classification uses a configurable neutral threshold so tiny price
movements around zero do not cause trades to constantly flip between
winner and loser classifications.

For example, with a neutral band of ±1%:

``` text
Winner   > +1%
Neutral  -1% to +1%
Loser    < -1%
```

# Efficient Price Updates

The application does **not** download price data separately for every
row in the master CSV.

Instead:

``` text
Master CSV
    ↓
Extract unique symbols
    ↓
Remove duplicates
    ↓
Batch-download market data
    ↓
Reuse downloaded data across all matching rows
    ↓
Calculate returns locally
    ↓
Update the master CSV
```

This is important because the same stock may appear multiple times
across different cohorts.

The application downloads market history by unique ticker rather than
performing a separate download for every historical signal row.

# GitHub Persistence

The master CSV can be stored in a private GitHub repository.

The workflow is:

``` text
GitHub Repository
        ↓
Load performance_database.csv
        ↓
Run Performance Terminal
        ↓
Freeze new cohorts or update performance
        ↓
Save updated CSV back to GitHub
```

This allows the historical database to persist even when:

-   Streamlit restarts
-   The app redeploys
-   The Streamlit filesystem resets

The GitHub repository acts as the persistent storage layer.

# Streamlit Secrets Setup

The GitHub credentials must be added to Streamlit Secrets.

Use:

``` toml
GITHUB_TOKEN = "your_github_personal_access_token"
GITHUB_OWNER = "your_github_username"
GITHUB_REPO = "your_repository_name"
GITHUB_BRANCH = "main"
GITHUB_CSV_PATH = "performance_database.csv"
```

Example:

``` toml
GITHUB_TOKEN = "github_pat_xxxxxxxxxxxxxxxxx"
GITHUB_OWNER = "yourusername"
GITHUB_REPO = "performance-terminal"
GITHUB_BRANCH = "main"
GITHUB_CSV_PATH = "performance_database.csv"
```

## Important

Do **not** place the GitHub token directly inside `app.py`.

Keep it only in:

``` text
Streamlit Secrets
```

or a local `.streamlit/secrets.toml` file that is excluded from Git.

# GitHub Token Permissions

The GitHub token must have permission to read and update repository
contents.

For a fine-grained personal access token, grant:

``` text
Repository permissions
    ↓
Contents
    ↓
Read and Write
```

Limit the token to the repository used for the Performance Terminal
whenever possible.

# Daily Workflow

## Step 1. Generate Signals

Run the main Nifty Market Terminal and generate the relevant:

-   Buy List
-   Confluence List
-   Emerging Setups, if supported
-   Other supported signal outputs

## Step 2. Freeze the Cohort

Import or select the signal output inside the Performance Terminal.

Review the cohort and freeze it. The app writes the new records into:

``` text
performance_database.csv
```

## Step 3. Update Performance

Use the Performance Update function.

The app:

1.  Loads the master CSV.
2.  Extracts unique symbols.
3.  Downloads available market data.
4.  Updates Trailing Profit.
5.  Fills any newly reached checkpoints such as 1W, 1M, or 3M.
6.  Saves the updated master CSV back to GitHub.

# Data Philosophy

The master CSV preserves the original signal history.

The application does **not** rewrite history by replacing old signals
with new ones.

A stock appearing multiple times remains visible in the raw signal
history because each appearance represents an actual scanner output.

The Consolidated Trades view is a separate analytical interpretation
generated from that same data.

This gives the system both:

``` text
Statistical signal analysis
```

and:

``` text
Practical investor-style trade analysis
```

without maintaining two separate databases.

# Important Notes

This application is a performance-tracking and analytical tool.

Market data availability can depend on the data provider and symbol
mapping. If a price cannot be retrieved for a symbol, the existing
historical record remains preserved and the unavailable checkpoint is
not fabricated.

The master CSV should remain the single source of truth for historical
performance records.

GitHub version history provides an additional layer of protection
against accidental deletion.
